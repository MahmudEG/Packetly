WINDOWS / FILE SERVICES

SMB access investigation planner

A successful port 445 test does not explain why a shared folder fails. Turn the observations you have into a focused next check, and export a handoff that separates evidence from assumptions.

For Windows clients and Windows file servers using SMB 2 or 3. This tool organizes observations you collect yourself; it does not connect to a server, execute commands, inspect your computer, or establish a root cause. Selections stay in this page and are not saved. Updated 25 November 2026.

What have you observed?

Check the name used in the UNC path, including its suffix. If several addresses are returned, record which address the connection test actually used.

A connection to another share or from another account does not establish access to this one.

Your investigation plan

Choose your observations, then build a plan. Unchecked evidence stays unknown; the planner will not fill in missing results.

Collect evidence without changing the system

Run these inspection commands in PowerShell on the affected Windows client. Replace the example name fileserver.example.com with the exact server name in your path. Use your existing approved access. Some properties or logs require elevation; an empty result in a different sign-in context is not equivalent to the affected user's result.

Resolve-DnsName -Name fileserver.example.com
Test-NetConnection -ComputerName fileserver.example.com -Port 445 -InformationLevel Detailed
Get-SmbConnection | Select-Object ServerName,ShareName,UserName,Dialect,NumOpens
Get-Service -Name LanmanWorkstation
Get-WinEvent -ListLog '*SMBClient*' | Select-Object LogName,IsEnabled,RecordCount

The TCP test creates a network connection attempt. The other commands inspect existing state. Discover available event channels before choosing one; channel names and available events differ by Windows release. Record a narrow incident time window rather than exporting every event.

Worked comparison: same symptom, different next check

These are fictional teaching observations, not captured customer output or claims of lab validation.

Case A: the name is wrong, but port 445 is open

An administrator expects the file server at 192.0.2.20. The name lookup and connection test both report 192.0.2.40, with TcpTestSucceeded: True. The useful finding is that transport reached the wrong endpoint. Before inspecting permissions on the intended server, reconcile the DNS record, search suffix, aliases and the target address. A port being open somewhere does not establish that the intended server was reached.

Case B: correct endpoint, open port, error 53

The lookup returns the intended address and the TCP test reaches it. The exact UNC path still reports error 53. Repeating the same port test adds little evidence. Record the client SMB events at the failure time, confirm the Workstation service state, and compare the same path on a known working client. On the server, an authorized administrator can inspect the SMB server events and share inventory. Keep negotiation and authentication as hypotheses until the events or a trace identify the failed stage.

Why this planner does not offer a one-click fix

Error text describes an outcome, not a universal cause. Enabling SMB 1, allowing guest access, disabling signing, opening every firewall rule or deleting all sessions can create a new problem while hiding the original evidence. The planner therefore recommends a next observation and explains the uncertainty. Any repair belongs in your normal change process after the failing boundary is identified.

Build an escalation someone can act on

The downloaded worksheet contains your selected observations and the matching next checks. Add the incident timestamp with time zone, client and server Windows builds, exact UNC path, resolved and contacted addresses, affected user context, and relevant event IDs before handing it to the responsible team. Remove private usernames, internal names and sensitive log content before posting publicly. Retest the original operation from the original client after a repair; a green TCP test by itself is not completion.
