Proxmox VE cluster quorum investigation cheat sheet

Inspect cluster membership and Corosync health when a Proxmox VE cluster loses quorum.

Proxmox VE 8 or 9 cluster; output depends on node, release and QDevice configuration.

Updated 2026-11-20 · Proxmox · 6 min read

CommandWhat it does
pveversionIdentify the Proxmox release
pvecm statusInspect quorum and votes

systemctl status corosync --no-pagerInspect the Corosync service
journalctl -u corosync --since "30 minutes ago" --no-pagerReview recent Corosync events

Walkthrough

Run read-only commands on authorized cluster nodes. Do not alter expected votes or cluster configuration during diagnosis; compare node views before arranging an approved recovery.

Step 1: Identify the Proxmox release

pveversion

Record the installed release and node identity before comparing cluster output with release-specific documentation and the approved configuration.

Step 2: Inspect quorum and votes

pvecm status

Record the current quorum status, expected votes and membership from this node. A partition may show a different view on another node; never infer its state from one node alone.

Step 3: Inspect the node membership view

pvecm nodes

Compare node IDs and vote counts with the documented membership. Review each accessible node separately to detect differing views or missing members.

Step 4: Inspect the Corosync service

systemctl status corosync --no-pager

Check service state and recent messages on the affected node. A running process does not prove that all cluster links are healthy or that the cluster has quorum.

Step 5: Review recent Corosync events

journalctl -u corosync --since "30 minutes ago" --no-pager

Compare timestamps and membership changes with the incident window. Logs may reveal a lost peer or link but should be correlated with network and node evidence.

WORKED INCIDENT

Practical case: A three-node cluster becomes non-quorate

Fictional teaching scenario; observations are examples, not captured production output.

Situation

An operator cannot make routine cluster changes after two Proxmox nodes become unreachable.

Investigation sequence

1. Identify the Proxmox release

pveversion

Identify the software release and the specific node providing each observation.

2. Inspect quorum and votes

pvecm status

Record quorum, expected votes and current membership on every accessible node.

3. Inspect the node membership view

pvecm nodes

Compare the displayed node list with the approved cluster inventory.

4. Inspect the Corosync service

systemctl status corosync --no-pager

Inspect Corosync service state and messages around the loss of quorum.

Example findings

Illustrative findings: one node reports itself as the only visible voter and network monitoring independently shows the other nodes are unreachable.

Interpret the findings

The membership view and independent network evidence point toward node or network recovery. Forcing votes without understanding partitions can create serious consistency risks.

Verify the outcome

After the owners restore the failed nodes or network through the approved recovery plan, compare membership and quorum on all nodes.

Escalation handoff

Share node-specific status, timestamps and sanitized Corosync logs with the virtualization and network teams.
