Microsoft Entra Conditional Access sign-in diagnosis cheat sheet

Use sign-in logs and policy results to investigate why a Conditional Access policy blocked an application sign-in.

Microsoft Entra admin center; access to logs, policy details and features depends on administrative roles, licensing and retention.

Walkthrough

These are portal procedures rather than commands. Use an authorized administrator account and handle sign-in details as sensitive information. Do not disable a policy to make the test pass.

Step 1: Open Entra sign-in logs and filter by user and time

Find the affected sign-in

Find the specific failed event using the user, application and approximate time. Account for time zone and retention; multiple retries can have different policy outcomes.

Step 2: Open the event and review its status and identifiers

Inspect the event details

Record the error, application, timestamp, correlation ID and sign-in context. Protect personal and device details when sharing the evidence with other teams.

Step 3: Open the Conditional Access tab for that event

Review Conditional Access results

Identify applied policies and inspect their reported results, including report-only results where available. A policy in report-only mode does not itself enforce a block.

Step 4: Inspect the relevant event details and policy requirements

Compare the device and sign-in context

Compare device state, application and other recorded conditions with the policy requirements. Missing or unexpected context can explain why a condition or grant control was evaluated differently than expected.

Step 5: Use the Conditional Access What If tool with the relevant scenario

Evaluate a proposed scenario

Enter the known user and conditions and inspect matching policies. This is a simulation, not proof of the original event outcome; the recorded sign-in remains the primary evidence.

Step 6: After the owner makes an authorized change, inspect a fresh sign-in

Validate an approved correction

Have the user retry through the normal application flow, then inspect the new event and policy results. Confirm the intended control still applies rather than relying solely on successful access.

WORKED INCIDENT

Practical case: A managed user cannot access an application

Fictional teaching scenario; observations are examples, not captured production output.

Situation

A user reports that a normally available cloud application suddenly blocks a sign-in.

Investigation sequence

1. Open Entra sign-in logs and filter by user and time

Find the affected sign-in

Find the exact failed event by user, application and approximate time.

2. Open the event and review its status and identifiers

Inspect the event details

Record its status and correlation identifier for a controlled investigation.

3. Open the Conditional Access tab for that event

Review Conditional Access results

Inspect the Conditional Access results for the policy and grant control involved.

4. Inspect the relevant event details and policy requirements

Compare the device and sign-in context

Compare the recorded device information with the relevant policy requirements.

5. Use the Conditional Access What If tool with the relevant scenario

Evaluate a proposed scenario

Use What If as a supplemental test with the known scenario details.

Example findings

Illustrative findings: the event shows a device compliance grant was not satisfied, and the device team confirms that the device has fallen out of compliance.

Interpret the findings

The event and independent device evidence identify the relevant control and a specific remediation lead; a policy match in a simulation alone would not establish the original failure.

Verify the outcome

After the device owner restores compliance, inspect a new sign-in and confirm the expected policy is enforced and satisfied.

Escalation handoff

Share the correlation ID, timestamp, policy name and sanitized device context with the identity and device administrators.
