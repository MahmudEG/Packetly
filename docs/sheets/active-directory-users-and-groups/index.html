Active Directory users and groups cheat sheet

Inspect domain identity, user status and group membership using RSAT.

On-premises Active Directory Domain Services; ActiveDirectory PowerShell module.

Updated 2026-11-02 · Active Directory · 6 min read

CommandWhat it does
Get-ADDomainIdentify the current domain
Get-ADUser -Identity 'jdoe' -Properties Enabled,LockedOut,PasswordLastSetInspect a user account
Get-ADPrincipalGroupMembership -Identity 'jdoe'List principal group memberships
Get-ADGroupMember -Identity 'Helpdesk'Inspect direct group members
Get-ADUser -Identity 'jdoe' -Properties MemberOfInspect direct group references on an account

Walkthrough

Install RSAT through your approved software process. Use a domain-connected administrative workstation and an account with directory read access.

Step 1: Identify the current domain

Get-ADDomain

Confirm DNSRoot, distinguished name and domain controllers. Querying the wrong domain can look like a missing user.

Step 2: Inspect a user account

Get-ADUser -Identity 'jdoe' -Properties Enabled,LockedOut,PasswordLastSet

Replace jdoe with a real sAMAccountName. Compare Enabled and LockedOut separately; neither field alone proves that sign-in will succeed.

Step 3: List principal group memberships

Get-ADPrincipalGroupMembership -Identity 'jdoe'

Review returned groups against expected access. This list is not a complete effective-access calculation across ACLs, claims and all resource domains.

Step 4: Inspect direct group members

Get-ADGroupMember -Identity 'Helpdesk'

Replace the example group. This returns direct membership; nested groups need separate inspection or the -Recursive parameter.

Step 5: Inspect direct group references on an account

Get-ADUser -Identity 'jdoe' -Properties MemberOf

Replace jdoe with the account. MemberOf describes direct membership references; evaluate nested groups and resource permissions separately.

WORKED INCIDENT

Practical case: A user cannot access a shared resource

Fictional teaching scenario; observations are examples, not captured production output.

Situation

A user can sign in but reports that a newly granted shared-resource permission is not working.

Investigation sequence

1. Identify the current domain

Get-ADDomain

Confirm DNSRoot, distinguished name and domain controllers. Querying the wrong domain can look like a missing user.

2. Inspect a user account

Get-ADUser -Identity 'jdoe' -Properties Enabled,LockedOut,PasswordLastSet

Replace jdoe with a real sAMAccountName. Compare Enabled and LockedOut separately; neither field alone proves that sign-in will succeed.

3. List principal group memberships

Get-ADPrincipalGroupMembership -Identity 'jdoe'

Review returned groups against expected access. This list is not a complete effective-access calculation across ACLs, claims and all resource domains.

4. Inspect direct group members

Get-ADGroupMember -Identity 'Helpdesk'

Replace the example group. This returns direct membership; nested groups need separate inspection or the -Recursive parameter.

5. Inspect direct group references on an account

Get-ADUser -Identity 'jdoe' -Properties MemberOf

Replace jdoe with the account. MemberOf describes direct membership references; evaluate nested groups and resource permissions separately.

Interpret the findings

Confirm the user and domain, account state and relevant direct or nested groups. Group membership is only one input to effective permissions and a fresh sign-in may be relevant.

Verify the outcome

Verify the intended resource access with the user after the approved group or permission change and review propagation where applicable.
