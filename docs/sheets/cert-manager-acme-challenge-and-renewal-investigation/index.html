cert-manager ACME challenge and renewal investigation cheat sheet

Inspect certificate, request, order and challenge status when cert-manager ACME issuance or renewal stalls.

Kubernetes with cert-manager and an ACME Issuer or ClusterIssuer; resource status and solver configuration depend on the installed version.

Updated 2026-11-20 · cert-manager · 6 min read

Walkthrough

Replace production and example-tls with actual resources. Use authorized read access. Do not print TLS Secret data, delete challenges or repeatedly trigger issuance during diagnosis.

Step 1: Confirm the Kubernetes context

kubectl config current-context

Compare the active context with the approved cluster inventory before reading certificate resources. A similarly named cluster may use a different issuer or DNS view.

Step 2: Inspect certificate status

kubectl describe certificate example-tls -n production

Record Ready conditions, issuer reference, renewal details and events. An existing certificate can still be served while a renewal attempt is failing, so inspect both status and expiry.

Step 3: Identify related certificate requests

kubectl get certificaterequests -n production

Find the request associated with the relevant certificate and issuance attempt. Names and revisions vary; use owner references and events rather than assuming the newest name is correct.

Step 4: Inspect ACME order status

kubectl get orders -n production

Identify the order associated with the request and record its state. Orders are specific to ACME issuance; other issuer types use different workflows.

Step 5: Find pending ACME challenges

kubectl get challenges -n production

List challenge resources associated with the order and note their state. A missing challenge may mean the workflow has not reached that stage or has already completed.

Step 6: Inspect the challenge reason

kubectl describe challenge CHALLENGE_NAME -n production

Replace the placeholder with the relevant challenge and read its reason and solver type. Treat self-check or validation errors as leads to investigate with the DNS or ingress owner.

WORKED INCIDENT

Practical case: An ACME certificate fails to renew

Fictional teaching scenario; observations are examples, not captured production output.

Situation

An operator notices that a certificate is approaching expiry while its replacement remains pending.

Investigation sequence

1. Confirm the Kubernetes context

kubectl config current-context

Confirm the correct cluster and namespace before collecting certificate evidence.

2. Inspect certificate status

kubectl describe certificate example-tls -n production

Inspect certificate conditions, issuer reference and recent events.

3. Identify related certificate requests

kubectl get certificaterequests -n production

Follow the associated certificate request and ACME order for the current attempt.

4. Inspect ACME order status

kubectl get orders -n production

Identify and inspect the relevant challenge status and reason.

Example findings

Illustrative findings: the HTTP-01 challenge reports a self-check failure and the ingress owner confirms the challenge path is routed to the wrong backend.

Interpret the findings

The challenge reason and independent ingress evidence identify a specific routing lead; a pending certificate alone does not identify the failed component.

Verify the outcome

After the ingress owner applies the approved fix, monitor the challenge and certificate status and verify the certificate actually presented by the service.

Escalation handoff

Share the namespace, resource names, challenge reason and sanitized ingress evidence with the certificate and platform owners.
