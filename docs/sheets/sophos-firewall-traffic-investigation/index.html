Sophos Firewall traffic investigation cheat sheet

Use log filters to connect a connection failure with firewall decisions.

Sophos Firewall SFOS web admin console; labels vary by version.

Walkthrough

Use a read-capable administrator account and a known source, destination and incident time. Availability of traffic records depends on rule logging.

Step 1: Open firewall traffic logs

Log viewer → Firewall

Set the time window for the reported failure. Confirm that the relevant firewall rule is configured to log traffic before treating an empty log as evidence of no traffic.

Step 2: Isolate a traffic flow

Filter source IP, destination IP and destination port

Use the translated and original addresses as appropriate to the scenario. Match the exact protocol and port; ping is not a substitute for an application flow.

Step 3: Read the firewall decision

Inspect action, rule ID and reason

Record the matching rule and drop reason. An allow record shows a policy decision at this device, not successful application authentication or the return route.

Step 4: Correlate adjacent failures

Compare with VPN and system events

If the destination is across a VPN, compare tunnel events and route state at the same timestamp. Preserve findings before proposing a scoped change.

Step 5: Review events for the matching firewall rule

Log viewer → filter by rule ID

After identifying the rule from a traffic event, narrow the time window and compare source, destination and actions. Missing records can reflect logging settings.

WORKED INCIDENT

Practical case: A new application flow is blocked

Fictional teaching scenario; observations are examples, not captured production output.

Situation

A client cannot reach an application through Sophos Firewall after a rule change.

Investigation sequence

1. Open firewall traffic logs

Log viewer → Firewall

Set the time window for the reported failure. Confirm that the relevant firewall rule is configured to log traffic before treating an empty log as evidence of no traffic.

2. Isolate a traffic flow

Filter source IP, destination IP and destination port

Use the translated and original addresses as appropriate to the scenario. Match the exact protocol and port; ping is not a substitute for an application flow.

3. Read the firewall decision

Inspect action, rule ID and reason

Record the matching rule and drop reason. An allow record shows a policy decision at this device, not successful application authentication or the return route.

4. Review events for the matching firewall rule

Log viewer → filter by rule ID

After identifying the rule from a traffic event, narrow the time window and compare source, destination and actions. Missing records can reflect logging settings.

5. Correlate adjacent failures

Compare with VPN and system events

If the destination is across a VPN, compare tunnel events and route state at the same timestamp. Preserve findings before proposing a scoped change.

Interpret the findings

A matching drop event and rule ID identify where to investigate. No event may mean logging was not enabled or the filter does not match the original or translated flow.

Verify the outcome

Retest the same source, destination and port after an approved change and compare the corresponding log event.
