AWS EC2 status check failure investigation cheat sheet

Distinguish EC2 system, instance and attached EBS status check failures before selecting a recovery path.

Amazon EC2 console with permissions to inspect instances and status checks; check availability depends on instance and volume type.

Walkthrough

These are read-only console procedures. Reboot, stop, recovery and replacement actions require the workload owner’s approved plan.

Step 1: Select the affected instance in the correct account and Region

Confirm the instance

Record the instance ID, Region and workload ownership. Similar instance names can exist in different accounts or Regions.

Step 2: Open the instance status and alarms information

Review individual status checks

Identify whether system, instance or attached EBS checks are impaired. A running instance state is separate from the individual health checks.

Step 3: Compare the failure start time with monitoring and changes

Review the timing

Record the first observed failure and correlate with metrics and recent changes. Correlation is a lead and does not alone establish a cause.

Step 4: Use the console system log for the affected Linux instance

Inspect available system logs

Review available boot and operating system messages for relevant errors, taking care to protect sensitive output. A log can be incomplete or stale.

Step 5: Provide the evidence to the instance and storage owners

Coordinate the recovery decision

Choose the documented recovery path for the specific failed check and workload. Rebooting or replacing an instance can affect availability and must follow the approved plan.

WORKED INCIDENT

Practical case: A running instance fails a health check

Fictional teaching scenario; observations are examples, not captured production output.

Situation

An operator sees an impaired EC2 instance while its lifecycle state still reads running.

Investigation sequence

1. Select the affected instance in the correct account and Region

Confirm the instance

Confirm the correct account, Region and exact instance ID.

2. Open the instance status and alarms information

Review individual status checks

Identify which individual instance status check is failing.

3. Compare the failure start time with monitoring and changes

Review the timing

Compare the failure time with monitoring and the change record.

4. Use the console system log for the affected Linux instance

Inspect available system logs

Inspect available system log evidence and involve the workload owner.

Example findings

Illustrative findings: the instance status check fails and the guest system log independently reports a boot-time filesystem error.

Interpret the findings

The check and log support a guest operating system investigation. The running lifecycle state does not prove that the guest is healthy.

Verify the outcome

After the owner completes the approved recovery, verify the individual checks and application service health.

Escalation handoff

Share the instance ID, Region, failed check, timestamps and sanitized log evidence with the cloud and workload teams.
