Kubernetes Pod pending scheduler investigation cheat sheet

Investigate FailedScheduling events, node allocatable resources, taints and Pod placement constraints.

Kubernetes with kubectl and authorized read access to Pods and Nodes; scheduler and autoscaler behavior varies by cluster.

Updated 2026-11-23 · Kubernetes · 6 min read

CommandWhat it does

Walkthrough

Replace production, web-pod and worker-1 with actual resource names. These commands inspect resources and do not change scheduling or workloads.

Step 1: Confirm the target cluster

kubectl config current-context

Compare the current context against the approved cluster inventory before interpreting events and node capacity from the API server.

Step 2: Inspect scheduler events

kubectl describe pod web-pod -n production

Read the node assignment, resource requests, tolerations and recent events. Pending can also mean image or volume setup, so confirm FailedScheduling before focusing on placement.

Step 3: List available nodes

kubectl get nodes -o wide

Compare node readiness and names with the intended node pool. Ready status alone does not establish sufficient allocatable resources or compatible placement constraints.

Step 4: Inspect node capacity and allocations

kubectl describe node worker-1

Review allocatable resources, requested totals, taints and conditions. Scheduling is based on requests and constraints rather than a simple reading of current CPU utilization.

Step 5: Inspect the Pod placement specification

kubectl get pod web-pod -n production -o yaml

Review requests, node selectors, affinity and tolerations for the affected Pod. Output may include environment configuration, so sanitize it before sharing.

WORKED INCIDENT

Practical case: A Pod remains pending on apparently idle nodes

Fictional teaching scenario; observations are examples, not captured production output.

Situation

A deployment has a pending Pod even though node CPU graphs appear mostly idle.

Investigation sequence

1. Confirm the target cluster

kubectl config current-context

Confirm the cluster and namespace of the pending workload.

2. Inspect scheduler events

kubectl describe pod web-pod -n production

Read the FailedScheduling events and identify the reported constraints.

3. List available nodes

kubectl get nodes -o wide

Compare available nodes and their readiness with the eligible node pool.

4. Inspect node capacity and allocations

kubectl describe node worker-1

Review allocatable CPU and requested totals on a relevant node.

5. Inspect the Pod placement specification

kubectl get pod web-pod -n production -o yaml

Compare the Pod requests and placement rules with the node details.

Example findings

Illustrative findings: eligible nodes have enough unused CPU at the moment, but their existing requested CPU leaves insufficient allocatable capacity for the new Pod.

Interpret the findings

The scheduler event and request totals explain this example. Low observed usage alone does not show that the scheduler can place the Pod.

Verify the outcome

After the platform owner approves a capacity or request change, inspect fresh scheduling events and verify the Pod becomes ready.

Escalation handoff

Share sanitized scheduler messages, requested resources and node allocation details with the workload and platform owners.
