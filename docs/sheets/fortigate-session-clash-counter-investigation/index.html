FortiGate session clash counter investigation cheat sheet

Investigate a rising session clash counter by comparing session statistics and routing over time.

FortiOS 7.4; command availability and output depend on model, VDOM and administrator privileges.

Updated 2026-11-16 · Fortinet · 6 min read

Walkthrough

Use an authorized read-only administrative session in the relevant VDOM. Record two samples with timestamps; these commands do not clear sessions or change traffic.

Step 1: Record version and system context

get system status

Record the FortiOS release and device identity so the statistics and troubleshooting guidance can be interpreted against the correct system and software.

Step 2: Inspect system health and uptime

get system performance status

Record uptime and resource pressure with the time of the sample. A large cumulative counter on a long-running device does not establish that clashes are occurring now.

Step 3: Inspect session counters

diagnose sys session stat

Record the clash count and other available session statistics. Compare a second sample over a known interval; a nonzero cumulative value alone does not demonstrate an ongoing incident.

Step 4: Inspect session status

get system session status

Review available session counts and protocol breakdown for context. Command output can vary by release and VDOM; session load does not by itself establish a clash cause.

Step 5: Review the routing table

get router info routing-table all

Compare the relevant routes and interfaces with the expected traffic path. Routing output is a point-in-time view and does not by itself prove asymmetric forwarding.

WORKED INCIDENT

Practical case: A new application has intermittent connections

Fictional teaching scenario; observations are examples, not captured production output.

Situation

An administrator sees a nonzero clash counter while investigating intermittent application traffic.

Investigation sequence

1. Record version and system context

get system status

Identify the device, relevant VDOM and software version before collecting evidence.

2. Inspect system health and uptime

get system performance status

Record system uptime and the time of the first observation.

3. Inspect session counters

diagnose sys session stat

Capture two clash counter samples and calculate the increase over the interval.

4. Inspect session status

get system session status

Review session status alongside the counter and the reported failure times.

5. Review the routing table

get router info routing-table all

Compare routes for both traffic directions with the documented network path.

Example findings

Illustrative findings: the counter rises during failures and the network team finds that return traffic follows an unexpected path.

Interpret the findings

The time correlation supports further investigation, while path evidence provides a separate lead. A clash counter alone cannot identify the responsible device or configuration.

Verify the outcome

After the network owner corrects the confirmed path through change control, compare fresh counter samples and application results over a similar period.

Escalation handoff

Share timestamps, sanitized counters, FortiOS version and routing observations with the firewall and network owners.
