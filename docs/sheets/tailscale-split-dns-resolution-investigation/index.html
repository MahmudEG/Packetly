Tailscale split DNS resolution investigation cheat sheet

Compare Linux resolver routing and tailnet connectivity when an internal domain does not resolve.

Linux using systemd-resolved and Tailscale; DNS management differs on other Linux configurations.

Updated 2026-11-25 · Tailscale · 6 min read

CommandWhat it does

tailscale statusInspect tailnet connectivity
resolvectl statusInspect resolver routing
resolvectl query host.internal.exampleQuery the affected name
tailscale ping server.exampleTest an authorized peer

Walkthrough

Replace host.internal.example and server.example with approved names. DNS queries and peer tests send network traffic.

Step 1: Record client version

tailscale version

Record the client version and host so the observed resolver behavior can be compared with the installed release and configuration.

Step 2: Inspect tailnet connectivity

tailscale status

Confirm the relevant peer is visible and record its state. An active peer does not establish that an internal DNS resolver or domain is reachable.

Step 3: Inspect resolver routing

resolvectl status

Review DNS servers and routing domains per interface. The resolver configuration can differ by distribution and must be compared with the intended split DNS domain.

Step 4: Query the affected name

resolvectl query host.internal.example

Replace the example with the approved internal hostname and record the answer or error. The result reflects the local resolver path at the time of the test.

Step 5: Test an authorized peer

tailscale ping server.example

Test the intended tailnet peer and compare direct or relayed connectivity. A successful peer ping does not prove that its DNS service or port is reachable.

WORKED INCIDENT

Practical case: An internal name fails on a remote laptop

Fictional teaching scenario; observations are examples, not captured production output.

Situation

A remote user can reach a tailnet peer but an internal service name does not resolve.

Investigation sequence

1. Record client version

tailscale version

Identify the affected client version and network environment.

2. Inspect tailnet connectivity

tailscale status

Inspect peer status and local resolver routing domains.

3. Inspect resolver routing

resolvectl status

Query the internal name using the system resolver and record the error.

4. Query the affected name

resolvectl query host.internal.example

Test the approved tailnet peer to separate basic peer reachability from name resolution.

Example findings

Illustrative findings: peer connectivity works, but the internal domain is absent from the configured resolver routing domains.

Interpret the findings

The missing route is a specific DNS configuration lead; tailnet connectivity alone does not establish that the internal resolver is used.

Verify the outcome

After the DNS owner corrects the approved split DNS configuration, repeat the query and test the application.

Escalation handoff

Share sanitized resolver domains, query result and peer status with the tailnet and DNS administrators.
