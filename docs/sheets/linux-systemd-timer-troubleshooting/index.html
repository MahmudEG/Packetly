Linux systemd timer troubleshooting cheat sheet

Inspect timer schedules, unit settings and service results when scheduled work does not run.

Linux distributions using systemd timers; commands inspect the system manager.

Updated 2026-11-11 · Linux · 6 min read

CommandWhat it does
systemctl list-timers --all --no-pagerList loaded timers and next runs
systemctl status backup.timer --no-pager --fullInspect a particular timer
systemctl cat backup.timerReview the timer and its drop-ins
systemctl status backup.service --no-pager --fullInspect the triggered service
journalctl -u backup.service --since "24 hours ago" -n 100 --no-pagerRead the service journal

Walkthrough

Replace backup.timer and backup.service with the actual units. Use an account permitted to read their journals. These commands do not start or change timers.

Step 1: List loaded timers and next runs

systemctl list-timers --all --no-pager

Compare NEXT and LAST with the expected schedule. The list includes loaded timers; absence alone does not prove no timer unit file exists on disk.

Step 2: Inspect a particular timer

systemctl status backup.timer --no-pager --full

Check the loaded path, active state and trigger information. A timer being active does not prove its associated service completed successfully.

Step 3: Review the timer and its drop-ins

systemctl cat backup.timer

Inspect the unit and drop-in files on disk, including scheduling directives and any Unit target. On-disk changes may differ from the manager state until configuration is reloaded.

Step 4: Inspect the triggered service

systemctl status backup.service --no-pager --full

Compare the last result and exit status with the expected job. A successful start is not necessarily a successful backup; verify the job output and backup artifact.

Step 5: Read the service journal

journalctl -u backup.service --since "24 hours ago" -n 100 --no-pager

Correlate the first error with the expected execution window. Journal permissions and retention affect which records appear, so no entries are not proof that nothing happened.

WORKED INCIDENT

Practical case: A scheduled backup is missing

Fictional teaching scenario; observations are examples, not captured production output.

Situation

The backup owner reports that the expected daily job did not produce a new backup.

Investigation sequence

1. List loaded timers and next runs

systemctl list-timers --all --no-pager

Record the timer listing and compare the next and last trigger with the schedule.

2. Inspect a particular timer

systemctl status backup.timer --no-pager --full

Inspect the exact timer active state and configured target.

3. Inspect the triggered service

systemctl status backup.service --no-pager --full

Check the corresponding service result and timestamp.

4. Read the service journal

journalctl -u backup.service --since "24 hours ago" -n 100 --no-pager

Review service journal messages from the reported job window.

Example findings

Illustrative findings: the timer fired on schedule, but the backup service exited with an error.

Interpret the findings

The timer fired in this example; the service failure is the next investigation. The result does not establish that older backups are restorable.

Verify the outcome

After an approved service correction, verify the next scheduled run, inspect its result and validate the backup through the normal restore-check process.

Escalation handoff

Provide unit names, trigger time, exit result and sanitized error messages to the backup owner.
