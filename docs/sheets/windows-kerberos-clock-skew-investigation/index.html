Windows Kerberos clock skew investigation cheat sheet

Inspect cached Kerberos tickets and Windows Time state when authentication reports excessive clock skew.

Domain-joined Windows 10 or 11 and Windows Server 2016 through 2025; event and access availability varies by host and permissions.

Updated 2026-11-23 · Active Directory · 6 min read

CommandWhat it does
klistInspect cached tickets
klist tgtInspect the ticket granting ticket
w32tm /query /statusInspect time service status
w32tm /query /sourceIdentify the active time source
w32tm /query /peersInspect configured time peers

Walkthrough

Run in the affected logon context with authorized access. Commands inspect tickets and time service state; they do not purge tickets or change the system clock.

Step 1: Inspect cached tickets

klist

Review ticket names and validity times in the current logon session. A cached ticket is evidence for that session, not proof that the failing application uses the same session.

Step 2: Inspect the ticket granting ticket

klist tgt

Review the current session ticket granting ticket and available time-skew information. Missing tickets can have several causes and do not by themselves establish clock drift.

Step 3: Inspect time service status

w32tm /query /status

Record the source, last successful synchronization and other status fields. A recent synchronization does not automatically prove alignment with the actual service or domain controller.

Step 4: Identify the active time source

w32tm /query /source

Compare the current source with the approved time hierarchy. A source different from expectations is a diagnostic lead and should be assessed in its operational context.

Step 5: Inspect configured time peers

w32tm /query /peers

Record peer status and compare it with the intended hierarchy. Check the relevant domain controller and target server separately when determining the actual time difference.

WORKED INCIDENT

Practical case: A domain user cannot authenticate to an internal service

Fictional teaching scenario; observations are examples, not captured production output.

Situation

A workstation receives a Kerberos clock skew error when accessing a domain service.

Investigation sequence

1. Inspect cached tickets

klist

Inspect cached tickets in the same logon context as the affected user.

2. Inspect the ticket granting ticket

klist tgt

Review the ticket granting ticket and any reported time-skew field.

3. Inspect time service status

w32tm /query /status

Record the Windows Time source and last successful synchronization.

4. Identify the active time source

w32tm /query /source

Compare configured peers with the approved domain time hierarchy.

5. Inspect configured time peers

w32tm /query /peers

Ask the domain owner to compare client, domain controller and service clocks.

Example findings

Illustrative findings: the affected client is several minutes out of alignment with the target service, and its time source is not the approved domain hierarchy.

Interpret the findings

The error and independently measured clock difference support a time synchronization investigation. A ticket listing or source name alone would not prove the root cause.

Verify the outcome

After the time owner restores synchronization using the approved process, compare clocks and retry the affected authentication flow.

Escalation handoff

Share sanitized event details, affected host names, timestamps and time-source observations with the domain administrators.
