DNSSEC validation failure troubleshooting with dig cheat sheet

Compare DNSSEC validation responses, delegation signer records and zone keys when a resolver returns SERVFAIL.

BIND 9 dig and an authorized validating resolver. Public and internal DNS views can legitimately differ.

Updated 2026-11-16 · BIND · 6 min read

CommandWhat it does

Walkthrough

Replace example.com, www.example.com and 192.0.2.53 with the affected zone and approved resolver. Queries send DNS traffic; the checking-disabled query is diagnostic only and must not replace validation for production applications.

Step 1: Inspect the validating resolver response

dig @192.0.2.53 www.example.com A +dnssec

Replace the documentation address and hostname. Record the response code, flags and answer. SERVFAIL is a general resolver failure and does not by itself prove a DNSSEC validation problem.

Step 2: Compare with checking disabled

dig @192.0.2.53 www.example.com A +dnssec +cd

The CD flag requests that the resolver not perform DNSSEC checking for this query. If the response differs, DNSSEC validation deserves investigation; this is not proof of a particular cause and must not become the application setting.

Step 3: Inspect the parent delegation signer response

dig example.com DS +dnssec

Query the affected zone’s DS record and identify the responding resolver. A cached response or a child-zone view can obscure the parent’s actual delegation; compare with an authoritative parent response when needed.

Step 4: Inspect the zone DNSKEY records

dig example.com DNSKEY +dnssec

Compare the returned public keys and signatures with the DNS provider’s expected active signing information. Key tags alone are not a complete DS digest validation; coordinate a full chain check with the DNS owner.

Step 5: Identify the zone nameservers

dig example.com NS

Record the delegation targets and compare them with the intended authoritative provider. Resolver caches, delegation changes and split DNS can make answers differ by location.

WORKED INCIDENT

Practical case: A domain fails only on validating resolvers

Fictional teaching scenario; observations are examples, not captured production output.

Situation

Clients report intermittent resolution failures after a DNS provider migration.

Investigation sequence

1. Inspect the validating resolver response

dig @192.0.2.53 www.example.com A +dnssec

Capture the response and resolver identity from the affected network.

2. Compare with checking disabled

dig @192.0.2.53 www.example.com A +dnssec +cd

Run the checking-disabled diagnostic against the same resolver and compare response codes.

3. Inspect the parent delegation signer response

dig example.com DS +dnssec

Inspect the parent delegation signer record for the affected zone.

4. Inspect the zone DNSKEY records

dig example.com DNSKEY +dnssec

Compare DNSKEY information with the intended authoritative provider.

Example findings

Illustrative findings: validation returns SERVFAIL, the checking-disabled query returns an answer, and the DNS owner identifies an outdated parent DS record.

Interpret the findings

The contrasting responses support investigating DNSSEC, and the independently confirmed outdated DS record explains this example. SERVFAIL or a successful CD query alone is not conclusive.

Verify the outcome

After the DNS owner corrects the delegation through the approved process, recheck the chain and query validating resolvers after applicable caching intervals.

Escalation handoff

Provide the domain, resolver, query times, response codes, DS and DNSKEY details to the DNS and registrar owners.
